The **cargo** fuselage shell is produced by `airframe/blender-scripts/merge_cargo_interior.py`
(Rev R1, 2026-06-30), NOT by `add_structural_features.py` (which now SKIPs cargo). It starts
from the clean Blender source, bakes to hull frame, and merges every cargo interior feature in
ONE `(shell + positives) − negatives` manifold3d expression. Output:
`airframe/stls/fuselage/cargo/cargo_sect_shell24_2mm_repaired.stl` — watertight, single body,
vol ≈ 323 188 mm³.

**MESH-01 root cause (fixed 2026-06-30):** it was NOT mainly the cutter-vs-wall epsilon; it was
`add_structural_features._subtract_all` subtracting cutters ONE AT A TIME via
`trimesh.boolean.difference(engine="manifold")` + per-step repair on a 1.4 M-face shell, which
compounded slivers into 10⁴+ bodies. Fix = union ALL cutters into one Manifold, do a SINGLE
difference (boolean of closed manifolds is closed ⇒ watertight out). Cutting a through-aperture
with a solid box keeps the mesh watertight (it becomes an open "cup" — still a closed 2-manifold).

**GOTCHA — the cargo SCAD interior modules are in a BROKEN legacy mental frame.** Only the WING +
nacelle-servo modules in `cargo_sect_shell24.scad` were reconciled to true hull frame (Rev R1
2026-06-22). The **GPS, FPV, door-servo-pad, latch-lip, and avionics-bay (Inara/River) modules
were authored with X=longitudinal, Y=vertical/dorsal, Z=lateral** — so `AVINICS_DORSAL_Y` etc. do
NOT map to correct hull positions through the bake transform (they'd land on the fwd joint face,
not the dorsal top). These were DEFERRED in the merge and must be RE-DERIVED in hull frame before
cutting the dorsal access panel / skin recesses. See [[project_r1_hull_frame_bake]].

Wing spar/mortise Y was re-derived (129 mm Rev R1 chord, LE root hull Y=−7 → spar 30% Y=+31.7,
mortise 50% Y=+57.5), superseding the stale-161 mm `WING_ROOT_Y_CEN=CY+40`. Lateral-wall/dorsal
features are seated against the mesh-sampled wall (walls curve inboard with Z; bbox extremity
floats off). Aft door hinge retention blocks (hull Y +109..+121) sit only ~9 mm from the aft
landing-leg row (Y≈100) — leg bosses must clear them.

## `feedback_generator_drift_and_freerouting.md`

---

---
name: feedback_generator_drift_and_freerouting
description: "When a board's gen_*.py no longer reproduces the checked-in .kicad_sch, inject rather than regenerate; how to autoroute via KiCad's Specctra DSN/SES bridge + freerouting"
metadata: 
  node_type: memory
  type: feedback
  originSessionId: 72cf1df7-3b8d-42f2-b896-bc45bb86ab02
  modified: 2026-07-26T22:31:24.842Z
---

**Generator drift**: before assuming a board's `gen_*.py` script is safe to re-run, diff its
output against the checked-in file's `kicad-cli sch erc` error count. Found 2026-07-26: running
Kaylee's `gen_kaylee.py` fresh from git HEAD (unmodified) produces 247 ERC errors where the real
checked-in `Kaylee.kicad_sch` has 0 — the generator had drifted from hand-tuning done at some
point in the KiCad GUI. **Why this matters**: full regeneration in this state would silently
destroy the working file. **How to apply**: when a generator has drifted, add new content via a
non-destructive text-injection script instead (parse the existing file, splice new lib_symbols/
body content in via balanced-paren-safe string insertion before the relevant closing parens, use
a distinct UUID-prefix stream to avoid collisions) — see `inject_kaylee_trust_module.py` and
`inject_emma_tpm.py` in `avionics/kicad/*/scripts/` for the working pattern. Re-verify by running
`kicad-cli sch erc` on the injected result.

**Also**: once the user has done manual PCB component packing/placement in the KiCad GUI, never
re-run the PCB-generation script (e.g. `gen_*_pcb.py`) without asking first — it will silently
overwrite that manual work. Confirmed by the user 2026-07-26 after this happened once with
`gen_can_periph_gw_pcb.py`.

**Freerouting an actual board in this environment**: `kicad-cli pcb export` has no DSN
subcommand and `pcbnew.PCB_IO_MGR` exposes no DSN plugin by name — but `pcbnew.ExportSpecctraDSN
(board, dsn_path)` / `pcbnew.ImportSpecctraSES(board, ses_path)` DO exist and work (verified
2026-07-26; an earlier guess at `pcbnew.ExportSpecctraFile` does not exist). See
`tools/export-specctra-dsn.py` / `tools/import-specctra-ses.py`. The bundled freerouting native
launcher (`bin/freerouting`) hangs waiting for a GUI with no display — invoke the JAR directly
with the system `java` instead: `java -jar <freerouting-dir>/lib/app/freerouting-executable.jar
-de <in.dsn> -do <out.ses> -mp <passes>`. Do NOT hand-roll a naive MST/straight-line autorouter as
a fallback — tried once, made DRC dramatically worse (114 unconnected → 266 violations including
48 real shorts) because it has no collision avoidance.

## `feedback_ground_clearance_requirement.md`

---

---
name: feedback-ground-clearance-requirement
description: "Ground clearance on Serenity is an aircraft-safety spec only, not sized to a cargo box's height — correction after I (Claude) misinterpreted it"
metadata: 
  node_type: memory
  type: feedback
  originSessionId: 8d7a83fc-067e-4887-ad99-15b4a8a6dd5c
  modified: 2026-07-26T18:16:56.822Z
---

Landing-gear ground clearance on the Serenity UAV is an **aircraft-safety
requirement only** (avoid a belly/tail strike, keep the hull clear of
ground debris during the landing/absorption stroke) — it is **not** sized
to let the parked aircraft straddle a cargo box's height. The 3×3×4 ft
cargo is carried internally; the aircraft **lands on top of** a
ground-staged cargo box with the cargo-bay doors open, then winches the
box into the bay. The gear never needs to clear the box while parked.

**Why:** I (Claude) inferred from the cargo box dimensions that the
landing gear needed enough ground clearance to fit the box underneath the
parked aircraft, and carried a ≥76 mm (3.0 in) requirement forward from
Rev R1 through Rev R6 on that basis. Steve corrected this 2026-07-23: the
real ops concept is land-over-then-winch-in, so the clearance minimum only
needs to satisfy flight safety, not cargo geometry. See
[[project_landing_gear_r6_variants]] for what changed as a result (the
1.5in/3.0in leg-length variant split in `docs/LANDING_GEAR_ANALYSIS.md`).

**How to apply:** Don't back-derive structural or geometric requirements
from a payload's physical dimensions unless the user has stated that the
payload must physically pass through/under/around that geometry. When a
requirement traces to "cargo needs to fit here," verify the actual
loading/unloading concept of operations first — on this project, cargo is
frequently handled by winching, docking, or other non-clearance methods
rather than physical pass-through.

## `feedback_kicad_hand_authoring.md`

---

---
name: feedback_kicad_hand_authoring
description: "Hand-authoring .kicad_sch — pin sheet_y = instance_y − lib_y; no ';' comments; verify by node count"
metadata: 
  node_type: memory
  type: feedback
  originSessionId: 0b104538-4478-49ff-91a6-9f2a40e2e90a
  modified: 2026-07-20T16:48:14.424Z
---

When hand-authoring KiCad schematics (`.kicad_sch` S-expr) in this repo, a placed
symbol's pins land at **sheet_x = instance_x + lib_x** but **sheet_y = instance_y −
lib_y** — the symbol library is Y-**up**, the schematic sheet is Y-**down**, so the Y
offset is **negated** (at rotation 0). X is not negated.

**Why:** I wired instance pins using `+lib_y` and silently **cross-wired every multi-pin
part**. Symmetric parts (a 4-pin pigtail) still passed `kicad-cli` ERC with 0 errors while
being wrong; only the AK7455's asymmetric pins exposed it (dangling-label / no-connect
errors). ERC error count alone does NOT prove correct connectivity.

**How to apply:**
- Compute each pin's sheet coord as `(instance_x + lib_x, instance_y − lib_y)`; place
  wires / power symbols / global labels / no_connects at those coords.
- Verify with `kicad-cli sch export netlist` and check **each net's node count** (e.g. a
  point-to-point signal must be 2 nodes), not just the ERC error total.
- KiCad's parser **rejects `;` semicolon comments** — do not put them in `.kicad_sch`
  (they cause "Failed to load schematic"). Use `(text …)` notes instead.
- Add `PWR_FLAG` on externally-supplied rails (pigtail-fed +3V3/GND) to clear
  `power_pin_not_driven`. Round-mm placement gives benign `endpoint_off_grid` warnings
  (matches existing repo schematics); inline symbols give benign `lib_symbol_issues`.
- Installed toolchain: **kicad-cli 9.0.2** (loads hand-written v7 `version 20231120` files).

See [[project_tilt_encoder_ak7455]], [[project_avionics_board_folder_reorg]].

Never leave a TODO.md item as `- [ ]` (open) once its own body text shows it's been resolved, superseded, or is no longer applicable. Close it out (`- [x]`) with a short pointer to whatever resolved/superseded it, even if that resolution is a later note already sitting right below it in the same item.

**Why:** Caught 2026-07-04 — TODO.md §1.1.1.1 had an item ("Verify head-cargo mating boss positions in slicer") whose own inline text said "RESOLVED 2026-06-29 ... obsolete", but the checkbox itself was still unchecked. A stale open box next to a written resolution is misleading — a reader (or a future me) scanning for open work will treat it as still-actionable.

**How to apply:** Whenever editing/reviewing TODO.md (and especially during any full-file pass like a Rev-letter consolidation), scan for items whose body text contains resolution language ("RESOLVED", "SUPERSEDED", "DONE", "obsolete", "no longer applicable", "fixed by X") while the checkbox is still `[ ]`, and flip it to `[x]`. Don't wait to be asked per-item — this is a standing rule for any TODO.md touch, not a one-off cleanup task. Related: [project_r1_hull_frame_bake](project_r1_hull_frame_bake.md) (the specific stale item was in the hull-frame-bake joint-boss thread).

→ TI MSPM0G3518-Q1** (`M0G3518QRHBRQ1`, VQFN-32 RHB, 5×5 mm) as of 2026-08-03.

Each pass has its own decision record in `PCB/`: `RS485-CANFD-TPM-upgrade.md`,
`S32K144-MCU-swap.md`, `MSPM0G3507-MCU-swap.md`, `MSPM0G3518-MCU-swap.md` (current).
Superseded docs are **kept with a banner**, not deleted — that is the repo's convention.

**The non-obvious trap:** MSPM0G**350x** and MSPM0G**351x** have very different security
silicon despite sharing the MSPM0 name, package and pinout. The '350x has *no* Customer
Secure Code (CSC), and without CSC there is no key store, no flash firewalls and no
monotonic counter. The '351x has CSC and therefore all of them. Authority is TI
**SLAAE29A** Table 1-2 (`M0G3x0x` column vs `M0Gx5 1x` column), local copy at
`Open-Secure-ESC/docs/datasheets/slaae29a.pdf`. Do not generalise "MSPM0 security" across
subfamilies. Datasheet **SLASFA6B** (`.../mspm0g3519-q1.pdf`) covers *both* G3518 and G3519.

**How to apply:** the '3507→'3518 swap moved no wires — the RHB-32 pad map is identical —
but the IOMUX `PINCM.PF` codes differ between the dies (e.g. `HFCLK_IN` 7→6, `TIMA0_C3`
5→8, `CAN0_TX/RX` 5/6→12). Pads staying put does not mean pin-mux config stays put.
Also: MSPM0 `NRST` **must** be pulled to VDD or the part never leaves reset, and `VCORE`
needs a dedicated 0.47 µF cap with nothing else on the net — both are new requirements
versus every earlier MCU on this board, which deliberately left reset unconnected.

horseshoe), and the continuous CF keel (CF-BAR-6X3) runs cargo→rear *through* the inner neck —

wall is an available hard load path. Relevant to the cargo/middle and middle/rear joint design

the user corrected it — the inner neck (closed) makes that false. It is in CLAUDE.md but is easy

## Bug: compute_bore_center used wrong initial centroid

`compute_bore_center()` in `blender_nacelle_integrated_v2.py` computed its initial

The Rev R6 landing gear (canonical articulated hip-pivot leg, replacing
the Rev R5 rigid vertical post) is split into two leg-length variants as
of 2026-07-23, per [[feedback_ground_clearance_requirement]]:

- **`canonical_leg_r6_1_5in.scad`** — 1.5 in (38.1 mm) belly clearance,
  **default**, wired into `airframe/FreeCAD-scripts/serenity_assembly.py`.
- **`canonical_leg_r6_3_0in.scad`** — 3.0 in (80 mm) belly clearance,
  **extended, kept** (not scrapped) for rough-field/extra-margin missions.
  This is the original 2026-07-21 Rev R6 design point.

Both share **identical bay, foot, and wire geometry** (confirmed
byte-for-byte via STL volume/bounds comparison) — only the leg-frame
`KNEE`/`ANKLE`/`GROUND_Z`/`R_H` skeleton constants differ. STL naming:
`lg_r6_1_5in_*.stl`, `lg_r6_3_0in_*.stl` for variant-dependent parts
(leg_frame, leg_assembled, leg_deformed, hull_legs, hull_stance);
`lg_r6_common_*.stl` for the shared bay/foot/wire parts — all in
`airframe/stls/fuselage/landing-gear/`.

**Key physics (both variants reuse the SAME wire hardware, solved once
against the 3.0in lever):** shortening the leg trades ground clearance for
higher peak deceleration, since ground force F = 2·P·r/R_h is inversely
proportional to the hip→foot arm R_h, while wire stroke (and hence hip
bending moment M = 2·P·r, and thus leg-frame structural margin) is
R_h-independent. At the 6 ft drop schedule: 1.5in runs 81 g tail-down /
162 g level with 15.5 mm residual clearance (no margin for a
single-ductile-wire-only arrest); 3.0in runs 52 g / 104 g with 44.9 mm
residual. Full numbers: `tools/landing_gear_r6_sizing.py` (parameterized
by `LEG_VARIANTS` dict) and `docs/LANDING_GEAR_ANALYSIS.md` Rev R6 §4.7.

The original undifferentiated `canonical_leg_r6.scad` (byte-identical to
the 3.0in variant) was retired and archived to
`archives/airframe-archives/archive/openscad/fuselage/` when the split was
made explicit.

**Open:** LG-17 (6 ft vs 4 ft ductile wire diameter, orthogonal to the
leg-length choice), LG-10 (bay flank-conforming bake), LG-18
(mass-reduction, targets differ per variant: ≤300 g for 1.5in / ≤350 g for
3.0in).

`nacelle_nozzle_iris.scad` Rev T3 (2026-08-09, user-directed). The nozzle has
`N_FLAPS` 8 x `FLAP_SPAN_DEG` 50 deg = **400 deg of arc on a 360 deg circle** —
a deliberate 5 deg inter-flap overlap documented since Rev R2. But every flap
was carved from the *same* radial band (`R_HINGE-FLAP_THICKNESS`..`R_HINGE`) at
the same radius, so that overlap was a solid **interpenetration**, not a lap
joint: physically unbuildable, and the exported asm STLs carried exactly
coincident cylindrical surfaces.

**Why it surfaced as a CI failure, and the diagnostic that matters:** coincident
faces export as edges shared by 4 facets (17 closed / 12 open) with **zero open
edges** — so it is NOT a hole. `trimesh.is_watertight` is False AND
`mesh.split()` returns **0 bodies**, which also defeats the multi-body fallback
in `tools/validate_stls.py`. If a Serenity STL fails watertight with 0 open
edges, look for coincident/touching faces between solids, not for gaps. See
[[project_scad_manifold_fixes]] for the same touching-face root-cause family.

**Fix:** alternate flaps are SEAL flaps lapped `FLAP_SHINGLE_GAP` = 0.2 mm
outboard of the MASTER flaps (master/seal arrangement, REFERENCES.md
**REF-CAD-005** = US 4,128,208, GE, expired/public domain). Both keep an
identical clevis on the hinge line, so all 8 still pivot on the same `R_HINGE`
circle and use the same unmodified hinge bosses — housing/throat/ring untouched.

**Load-bearing invariant:** the MASTER band is unchanged, so
`exit_r(phi) = R_HINGE - FLAP_LENGTH*sin(phi)` and the CLAUDE.md 75%/105%
bore-percentage targets are numerically unaffected. Verified: flow-boundary min
radius 16.311 mm and max 35.600 mm identical before/after, and the print-ready
master STL renders byte-identical geometry (1702 facets, 2636.5722 mm^3). A
naive radial *translate* of the whole flap would instead move the clevis off its
hinge boss — shift the panel's curvature band, never the flap.

**Consequences to remember:** flap print count is no longer 8 identical — it is
**4 master + 4 seal per nozzle** (`RENDER_PART` "flap" / "flap_seal"), BOM
`PRINT-NACELLE-FLAP-MASTER`/`-SEAL`. Flap-set mass 32.0 -> 56.8 g (+24.8 g),
all aft/outboard of the tilt pivot — Rev T CG band (~109-112 mm) still needs
re-verification. `FLAP_PHI` is now a parameter so each asm STL is reproducible.
`nacelle_nozzle_iris-closed-5deg.stl` was an abandoned earlier shingling attempt
from a source revision no longer in the tree (phi=5 reproduces neither its facet

All 16 SCAD files in serenity/stl/ now render Simple:yes (manifold) as of 2026-05-26.

## Root causes and fixes

**touching-face / coplanar surfaces** — the main failure mode across multiple files.
Any geometry that merely touches (is tangent to) another surface at exactly one plane
creates non-manifold edges in CGAL boolean output. Fix: extend the offending solid 1 mm
past the contact surface so the union has genuine volumetric overlap.

**Why:** CGAL requires closed 2-manifolds; touching faces violate the edge-manifold invariant.

**How to apply:** Whenever adding a boss, web, conduit, or arm that butts up against a
cylindrical or planar surface, offset the root by -1 mm (into the surface) and add 1 mm to
the height to keep external geometry unchanged.

## Specific fixes

- `s_aft_edf_plenum.scad` — four inlet arms ended exactly at hub outer radius (CENTRE_R+WALL=23mm).
  Fix: extend `_inlet_arm()` by +1 in ARM_LEN and TAPER_L so arms penetrate hub 1 mm.

- `nacelle_pod_50mm_tandem.scad` — three touching issues:
  1. `nav_wire_conduit`: cube started at face_x (nacelle outer X surface). Fix: x_offset − 1,
     cube width + 1, bore_cx adjusted for pylon_side=+1.
  2. `pivot_x_face_boss` cylinder: started at face_x. Fix: translate by (OD_X/2 − 1), h +1.
     Also changed rotate([0,90,0]) to rotate([0,sign*90,0]) so −X boss goes outward, not inward.
  3. Load-spreading web (rectangular polygon): top face tangent to boss cylinder bottom at Z=75.
     Fix: replaced rectangular polygon + linear_extrude with hull() between a ring (at boss root)
     and a disc (at nacelle face), creating a conical fillet with no coplanar surfaces.

## Gear-file CGAL timeouts

**Why the crew nicknames matter:** the user refers to boards by aircrew role, not
repo name — "observer" = Jayne, "flight engineer" = Kaylee. Nothing in the repo
records that mapping; it was inferred from those being the only three boards
carrying an MSPM0G3507 and confirmed by the user.

**Key facts established (all datasheet-verified, don't re-derive):**

- MSPM0G351x-Q1 RGZ-48 pin map is **bit-identical** to MSPM0G350x/-Q1 RGZ-48
  (SLASFA6B Fig 6-5 vs SLASEX6C/SLASF88C Fig 6-4). Symbol geometry was reused.
- RHB-32 bonds out **PA0–PA27 only — no PBx port exists**. That is what forces the
  re-pinmux on the two 32-pin boards.
- Same pins, different IOMUX on this family: CAN is `CAN0_TX`/`CAN0_RX` at **PF12**
  (was PF5/PF6); PA15 offers `SPI1_CS2`, not `SPI1_CS0`; PB15/PB16 offer UART7, not
  UART2. Wiring unchanged, **firmware pinmux constants must change**.
- SLB9672 is pin-compatible with SLB9670 for every pin these boards use; only
  pins 3/4/6/7 differ, all unconnected here.

**Pre-existing defects this work uncovered (see TODO.md §1.2d):**

- The MCU land was `QFN-48-1EP_7x7mm_P0.5mm_EP5.15x5.15mm`, which KiCad's own
  `descr` identifies as an **Analog Devices LTC legacy** outline. TI RGZ0048F's
  exposed pad is 4.1 mm. Corrected to `VQFN-48...EP4.1x4.1mm`.
- The SLB9670 symbol had **no pad 33**, so every TPM's exposed pad was floating.
- **Kaylee's `U_MCU`, `U_TPM` and `U_ISOCAN` symbols are drawn stacked on top of one
  another.** 17 MCU pads shared a coordinate with a TPM pad, so one global label
  served both symbols — shorting the TPM SPI bus and tying MCU VCORE to TPM GND.
  I first misread these as "stale duplicate labels from a superseded draft" and
  deleted them, which broke the TPM. Correct fix was to move `U_TPM` +34.29 mm and
  re-emit its labels, *preserving* labels belonging to the third stacked symbol.
  **If a Kaylee label looks duplicated, check for symbol overlap before deleting it.**
- Kaylee's board ground net is named `CM2_OUT_N` (108 nodes) — a current-monitor
  output label mis-merged with `PGND`. Not fixed; out of scope.

**Committed `.net` files were stale** on both Jayne and the gateway — they disagreed
with the live schematics. Always regenerate with `kicad-cli sch export netlist`
rather than trusting the checked-in `.net`.

they carry a superseded-part guard header now; see
